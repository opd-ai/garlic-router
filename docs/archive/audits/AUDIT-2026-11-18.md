## 2. What was fixed

### 2.1 Wire format (STATIC defect, now covered by golden vectors)

- **TunnelGateway body omitted the spec's 2-byte length** (previous audit F-01,
  `I2NPMessages.swift`). `I2PTunnelGatewayPayload` now encodes
  `tunnelID (4) | length (2) | message` and its parser rejects a length that
  under- or overruns the body. The old shape was invisible to the suite because
  every test round-tripped the struct through itself.
- **`Data` body omitted its 4-byte length** (F-02). Added `I2NPDataMessage`,
  used by `parseBody()` and by all three live producers/consumers (eepsite
  client, IRC stream client, SAM session), so a Data message on the wire is now
  `length (4) | payload`.
- **Short-header parsers indexed `Data` from absolute zero** (F-07). `parseShort`
  and `looksLikeShortHeaderMessage` now rebase through `Array(data)` first, so a
  slice with a non-zero `startIndex` can no longer trap on network input.

### 2.2 Truth table (F-03)

`NP-TUNGW` now states the real layout and its test list; `NP-GARLIC` no longer
names two wrong type codes (it reads `I2NPMessageType.garlic.rawValue`); the new
`NP-DATA` row documents the Data body. The `TN-GW` row's "type 15" is now read
from the enum. The table can no longer drift from the codes the router emits
without the enum changing too.

### 2.3 Client logic

- **RTT reading was always amber** (`I2PIRCLatency.isSlow`): it compared a
  millisecond count against a threshold stated in seconds, so every reading
  above 2 ms counted as slow. Now `milliseconds > 2000`.
- **Channel-scoped numeric errors went to the wrong conversation**
  (`I2PIRCChannel`): the router filed them by `params[0]` (our nick) and dropped
  the channel, so even "you are not a channel operator" landed in the server
  buffer, with the channel name glued into the sentence. It now uses `params[1]`
  when that is a channel we hold, and strips our nick and the channel name from
  the sentence.
- **Address-bar suggestions matched the shared TLD** (`I2PSavedHostsStore`):
  every saved host ends in `.i2p`, so typing "i2p" listed the whole book list.
  Matching is now on the host without its suffix; completion keeps a prefix match
  on both forms so "planet.i" still completes.

### 2.4 Build and test infrastructure

- **The unit test target could not build**: `IPHONEOS_DEPLOYMENT_TARGET = 18.5`
  while the app target is 26.0, so `@testable import Untitled1` failed with
  "compiling for iOS 18.5, but module 'Untitled1' has a minimum deployment target
  of iOS 26.0". CI runs `xcodebuild test`, so its test step could never have
  passed. Both test configurations now say 26.0 (the only project-file change in
  this pass, made because no tool exposes build settings).
- **CI ran an empty test target** (F-04). `Untitled1Tests/I2PProtocolTests.swift`
  runs the cross-validation suite, the core suite, the client-logic suites and a
  truth-table/type-code check, so the protocol layer is now gated by `xcodebuild
  test`.
- **Harness rot** (F-09, partially): `SelfTestProbe/ProbeStubs.swift` now carries
  the two stand-ins the documented command needs, so that command works as
  written. `NetDiag`, `LiveProbe` and `MainnetProbe` used `@main` inside a file
  named `main.swift`, which the compiler rejects; they are top-level code again.
- **Swift 6 future break** (F-10): `I2PSavedHostsRefresh` no longer captures a
  mutable `var` across the `MainActor.run` hop.

### 2.5 Stale assertions (F-05 triage)

Nine failures were triaged one by one. Two were code defects (latency, numeric
routing), one was a product-behaviour mismatch in a fixture (bookmark matching),
and the rest were assertions that could not hold as written:

| Test | Why it failed | Resolution |
| --- | --- | --- |
| `irc · channel, nick-prefix and text rules` | the split fixture was 269 bytes against a 400-byte ceiling, so it never split | fixture is now > 400 bytes and the ceiling is asserted first |
| `irc · notices, actions, topics…` | the numeric fixture named a channel we do not hold | fixture names `#i2p`; a second case keeps the "not ours" behaviour |
| `irc · private queries, nick changes…` | asserted the nick was still in the roster *after* her QUIT | assertion split: present after NICK, gone after PART/QUIT |
| `irc · MODE moves nicks…` | expected a sorted roster from an insertion-ordered array | compares sorted keys; membership is what the rule is about |
| `irc · history saves a transcript…` | expected the server's 001 sentence in the buffer, which is summarised into the connect line | asserts the connect line the buffer actually saves |
| `irc · a snooze is kept per server…` | asserted an hour-long snooze was *not* live 15 seconds in | asserts it is live |
| `saved hosts · address bar suggestions…` | the "i"-query expectation only held under TLD matching | asserts label matching and keeps the never-visited-last case |

The 3 remaining failures in the last line are one environment artefact plus its
two roll-ups: `T4-ND-SU3-SIGNER` loads the reseed certificates from the **app
bundle** (`Resources/reseed-certs`), which does not exist in a bare `swiftc`
binary. It passes in the app and in the unit test target, not off-device.

The new golden vectors (`T4-NP-TUNGW-RT`, `T4-NP-DATA-RT`) assert literal spec
bytes in both directions and reject short, trailing and header-only bodies —
the class of test that would have caught F-01 and F-02.

## 4. Live mainnet probe (VERIFIED, non-disruptive)

`NetDiag` was compiled and run once from the build Mac: one reseed fetch, then
outbound NTCP2 dials to at most three floodfill routers chosen from the fresh
netdb. No scanning, no retries against unresponsive hosts, no published state of
ours beyond what the probe itself needs.

```
OUR RI published=… sigOK=true  options=[router.version 0.9.70, netId 2, caps O]
reseed: https://reseed.diva.exchange/ ingested=75 rejected=0 floodfills=57
dialed 3 floodfills (23.128.248.7:7777, 163.245.216.254:31452, 95.190.33.140:15875)
sessions: 1   summaries: ["099ae2967a0d"]
closes:
  0ccb5e7a0726: peer closed during the handshake after SessionRequest (no SessionCreated)
  15495e86c453: handshakeFailed("peer did not accept the TCP connection within 8s")
```

What this supports: reseed and RouterInfo ingestion work against the real
network (75 entries, 0 rejected, 57 floodfills), and one NTCP2 handshake to a
mainnet floodfill was still established at the end of the 20-second window.

What it does **not** support: no outbound tunnel was built, no LeaseSet was
resolved over the network, no garlic message was delivered, and nothing was sent
*to us*. The two peers that closed after SessionRequest are exactly the case that
still cannot be diagnosed from our side — the peer's reason is only visible in
its own log.
