## 5. Findings and remediation

Ordered by practical impact. Each gives evidence, affected component, expected
versus observed, a reproduction path, and a fix.

### 5.1 F-01 — HIGH — `TunnelGateway` payload is missing the spec's 2-byte length

**Component:** `Untitled1/I2P/I2NPMessages.swift:273-290` (`I2PTunnelGatewayPayload`).

**Specification** (I2NP §TunnelGateway, fetched 2026-11-17):

```
+----+----+----+----+----+----+----+-//
| tunnelId(4)       | length(2) | data...
tunnelId :: 4 byte TunnelId
length   :: 2 byte Integer, length of the payload
data     :: $length bytes, an I2NP message with a standard 16-byte header
```

**Observed:**

```swift
// serialize()
w.integer(gatewayID)
w.raw(message)              // ← no 2-byte length
// parse()
let id = try r.integer()
let message = try r.raw(r.remaining)   // ← consumes everything
```

The payload is `[gatewayID][message]` instead of `[gatewayID][length][message]`.

**Expected vs observed:** a reference gateway parses a 2-byte length from what we
believe is the first two bytes of the inner I2NP message. The inner message
begins with its type byte (e.g. `0x0B` for Garlic, `0x13` for TunnelGateway), so
the peer reads a bogus 2-byte length and either drops the message or over-reads.
Inbound, the two length bytes are prepended to the inner message, so our own
`I2NPMessage.parse` sees a corrupt type/size.

**Affected call paths — all on the live send path:**

- `I2PGarlic.swift:607-609` — wrapping a garlic message for a LeaseSet's gateway;
- `I2PGarlic.swift:699-705` — clove-driven tunnel delivery;
- `I2NPPipeline.swift:132` — the innermost payload a tunnel's last hop delivers;
- `I2PLiveMainnetChecks.swift:346-348` — the mainnet build-reply probe.

Consequence: **garlic delivery to any remote destination is malformed**, which
breaks the eepsite browser, IRC over I2P, and build-reply delivery — the three
user-facing consumers of this path.

**Why the suite did not catch it:** `I2PCrossValidation.swift:1329-1341`
(`T4-NP-TUNGW-RT`) serialises with the same struct and parses with the same
struct, so both directions are wrong symmetrically and the bytes match.
`I2NPTests.swift:141-144` asserts the same shape. The truth-table row
`NP-TUNGW` (`I2PSpecTruthTable.swift:459-469`) documents the *wrong* layout as
canonical ("gatewayID (4 BE) + message bytes"), which is why it was never
re-examined; its status is honestly `pendingWireVerification`.

**Reproduction (authorised local only):** build the harness, then add to any
scratch driver:

```swift
let p = I2PTunnelGatewayPayload(gatewayID: 0x11223344,
                                message: Data([0x0B, 0, 0, 0, 1])).serialize()
// observed 9 bytes: 11 22 33 44 0B 00 00 00 01
// spec     11 bytes: 11 22 33 44 00 05 0B 00 00 00 01
```

**Remediation:**

```swift
func serialize() -> Data {
    var w = I2PWriter()
    w.integer(gatewayID)
    w.short(UInt16(clamping: message.count))
    w.raw(message)
    return w.data
}

static func parse(_ data: Data) throws -> (gatewayID: UInt32, message: Data) {
    var r = I2PReader(data)
    let id = try r.integer()
    let length = Int(try r.short())
    let message = try r.raw(length)
    guard r.remaining == 0 else { throw I2PWireError.trailingData }
    return (id, message)
}
```

**Test to add:** a golden vector, not a round trip — a fixed byte string taken
from a Java I2P `TunnelGatewayMessage` (or hand-assembled from the spec diagram
above), asserted for exact equality in both directions, plus a
length-mismatch and a trailing-data rejection case. Tag it to `NP-TUNGW` and flip
the truth-table row from `pendingWireVerification` to `aligned` only once it
passes.

**Caveat:** this finding is STATIC. The defect is objective in the source and the
spec, but it has not been observed failing against a real peer, because no peer
was authorised.

### 5.2 F-02 — MEDIUM — I2NP `Data` message omits its 4-byte length

**Component:** `I2NPMessages.swift:200-201` (parse) and `:217-228`, `:222`
(`.dataMessage(Data)`).

**Specification** (I2NP §Data): `length (4 bytes) + data`, "used inside Garlic
messages and Garlic Cloves". The 9-byte short header note also names
"ECIES-Ratchet Garlic Cloves" as a consumer.

**Observed:** the case carries the payload opaquely and neither writes nor strips
the 4-byte length. A `Data` message received in a clove yields a payload
prefixed by 4 bytes that are not data; a `Data` message we emit is 4 bytes short.

**Remediation:** give `.dataMessage` a length-prefixed codec
(`w.integer(UInt32(payload.count)); w.raw(payload)` / read length, read exact
bytes, reject trailing). Add the same golden-vector treatment as F-01.

### 5.3 F-03 — MEDIUM — the spec truth table contains wrong spec claims

**Component:** `Untitled1/I2P/I2PSpecTruthTable.swift`, the artifact the
Alignment report renders and the roadmap cites as the compliance baseline.

- `NP-TUNGW:465` — "Type code 7 per spec". The spec says TunnelGateway is **19**.
  The implementation (`I2NPMessages.swift:32`) correctly uses 19. The document is
  wrong, not the code.
- `NP-GARLIC:471` — the row title says "GarlicMessage wrapping (type 21)" and
  `:476` says "type 5 per spec". The spec says Garlic is **11**; the
  implementation correctly uses 11. Both prose claims are wrong.
- `NP-TUNGW:464` — the wire layout itself omits the length field (F-01).

**Impact:** the truth table is the document used to justify `aligned` status for
43 rows. Three of its own claims are demonstrably wrong. Any "aligned" status it
carries must therefore be treated as an assertion by the authors, not as audit
evidence — precisely the distinction this audit exists to draw.

**Remediation:** stop restating type codes in prose. Have the table reference
`I2NPMessageType` (`"type \(I2NPMessageType.tunnelGateway.rawValue)"`) so the
document cannot drift from the enum, and add a test that walks the table and
compares each declared code with the enum's raw value.

### 5.4 F-04 — MEDIUM — CI executes none of the I2P test suite

**Component:** `.github/workflows/ci.yml:101-112`, `Untitled1Tests/*`,
`Untitled1UITests/*`.

**Evidence:** 0 `XCTAssert` in the unit target; the sole `@Test` has an empty

**Impact:** every regression in the protocol layer ships green. F-01, F-02 and


Then add the same shape for `I2PSelfTest.runAll()` once §3.4 is triaged. The
suites are already `static` and dependency-free, so this is a thin adapter, not
new test infrastructure.

### 5.5 F-05 — MEDIUM — 9 of 173 self-test assertions fail and nothing notices

**Evidence:** §3.4, reproduced with the exact command in §1.5.
**Impact:** at least six of the nine are environment-independent logic

**Remediation:** triage each failing guard; fix the code or the assertion; then

### 5.6 F-06 — MEDIUM — SSU2 is not wired into the running router

**Component:** `I2PRouterAppContext.swift` contains no reference to SSU2.
`SSU2Transport|SSU2Session|I2PSSU2Engine|SSU2Host|SSU2Router` appear only in
`I2PSSU2.swift`, `I2PSSU2Crypto.swift`, `I2PProductionAudit.swift` and
`I2PSpecTruthTable.swift`.

**Impact:** the router is NTCP2-only. It cannot be reached over UDP, cannot
publish a usable SSU2 address, and cannot be selected as a hop by SSU2-only
peers. The SSU2 module's own tests pass, including the ML-KEM hybrid paths, but
they exercise a component nothing dials. This matches `INTEROP_REPORT.md:27-30`.

**Remediation:** wire the transport into `I2PRouterAppContext` (listener, dial,
RouterInfo `SSU2` address with intro key) and add one integration test that
dials the wired transport over UDP loopback through the app context rather than
through the module directly.

### 5.7 F-07 — LOW/MEDIUM — short-header parser indexes `Data` from absolute zero

**Component:** `I2NPMessages.swift:162-176` (`data[0]`, `data.subdata(in: 9..<data.count)`)
and `:181-183` (`data[0]`).

**Why it matters:** `Data` carries its own index base. On a slice whose
`startIndex != 0`, `data[0]` traps and `subdata(in:)` returns the wrong bytes.
This is the exact crash class already recorded twice in `BUGLOG.md` (BUG-001
note: "non-zero `Data` index bases from CryptoKit seals"). The current inbound
caller (`I2PNTCP2.swift:412-413`) is fed by `NTCP2Block.decode` → `I2PReader.raw`,
which re-bases through `Array`, so the path is **safe today** — but it is one
refactor away from a remote-triggerable crash in a parser fed by the network.

**Remediation:** make the function total: `let bytes = Data(data)` at the top, or
index with `data[data.startIndex]` and use `data.dropFirst(9)`.

### 5.8 F-08 — LOW — `precondition` in crypto and wire-encoding paths

**Component:** `I2PNTCP2Crypto.swift:261-288` (`I2PAESCBC.crypt`),
`I2PBinary.swift:42-53` (`hash`, `string`), `:59-73` (`mapping` casts
`UInt8(k.count)`, which traps instead of throwing above 255 bytes),
`I2NPMessages.swift:244-251` and `:311-324` (struct preconditions).

**Why it matters:** a trap is a process crash, not a rejected message. These sit
on the transport queue and are reachable from remote data through upstream bugs.
No reviewed path currently reaches them with bad input, so this is hardening, not
a live defect.

**Remediation:** convert to `throws` on the network-facing boundaries; keep
`precondition` only for programmer errors that cannot be driven by input.

### 5.9 F-09 — LOW — the documented off-device harness command no longer builds

**Component:** `SelfTestProbe/main.swift:7-9` vs `I2PSelfTest.swift:100-101` and
`EepsiteBrowserView.swift:1634`, `:1730`.
**Impact:** the project's only way to execute its own suites outside a simulator
is broken by a copy-paste, and the only way to notice was to run it.
**Remediation:** either move the two browser self-test enums into `I2P/` (they are
pure logic and have no SwiftUI dependency), or update the documented command to
include the needed files. Prefer the first — self-tests inside a 1799-line view
file are what caused the rot.

### 5.10 F-10 — LOW — Swift 6 will fail the build

**Component:** `I2PSavedHostsRefresh.swift:151`
("reference to captured var 'failed' in concurrently-executing code; this is an
error in the Swift 6 language mode").
**Remediation:** capture into a local `let` before the `MainActor.run` hop.
